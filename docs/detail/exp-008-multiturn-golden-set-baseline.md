# EXP-008 골든셋을 멀티턴 대화로 확장 + eval 러너 턴 지원 — 컨텍스트 주입 전 베이스라인

- **날짜**: 2026-09-08
- **상태**: ✅ 채택

## 배경 / 가설

멀티턴(대화형 후속 질문) 지원을 설계하면서, "지금 구조로 멀티턴이 가능한가"부터 "직전 턴 컨텍스트를 intent/sql_generation 프롬프트에 주입하면 후속 질문 정확도가 얼마나 좋아지는가"까지 이어지는 작업을 하나의 KPI 실험 계열로 진행하기로 했다. 다만 지금 시점엔 GraphState에 `conversation_id`/`turn_no`/`carry_schema`/`prior_turns` 필드만 배관돼 있을 뿐 **어떤 노드도 아직 이 값을 읽지 않는다** — 즉 아직 컨텍스트 주입 코드가 없는 상태다. 프롬프트 주입(다음 실험)의 효과를 재려면 그 전에 "컨텍스트 없이 후속 질문을 시키면 얼마나 틀리는가"를 먼저 실측해 두어야 대조가 가능하므로, 이번 실험은 EXP-001과 같은 성격의 **baseline 확보용**이다 — 코드/프롬프트를 바꾼 게 아니라, 후속 질문이 포함된 골든셋과 그걸 턴 단위로 돌릴 수 있는 eval 러너 자체를 처음 만들고 그 결과를 최초로 잰 것.

## 변경 내용

- `server/domains/poc_prostate/golden_set.json`: 포맷을 `[{question, expected_sql}]`(19문항) → `[{"turns": [...]}]`(대화 단위, 19개 싱글턴 대화로 그대로 마이그레이션 + 후속 질문이 있는 대화 4개 신규 작성) — 총 23개 대화, 28턴. 새 대화 4개는 실제 target DB에 쿼리를 직접 돌려 `expected_sql`을 검증한 뒤 작성(필터 유지+테이블 확장, 필터만 추가, 차원 추가, 지표 자체가 바뀌는 패턴 각 1개씩)
- `server/app/graph/conversation_context.py`(신규): `extract_prior_turn()`을 API(`app/api/run_routes.py`)와 eval이 공유하는 핵심 로직으로 분리 — API는 `run_manager`에 영속화된 직전 턴을 읽어 쓰고, eval은 `graph.invoke()`가 반환한 GraphState를 메모리에서 바로 넘겨 씀(골든셋 실행이 `runs`/`conversations` 테이블을 오염시키지 않도록 — EXP-001에서 확인한 "eval 실행은 실행 히스토리 화면에 안 잡혀야 한다"는 기존 관례를 그대로 따름)
- `server/eval/execution_accuracy.py`: `run()`을 대화→턴 이중 루프로 재작성. 대화 경계에서 `prior_turns`를 리셋하고, 성공적으로 끝난 턴만 다음 턴에 컨텍스트로 넘김(golden-set 정답 일치 여부가 아니라 "생성이 끝까지 성공했는가"라는 실서비스 기준을 그대로 사용). `turn_no`를 `tags`에 남겨 결과에 `by_turn_no` 브레이크다운 추가
- `server/app/api/eval_routes.py`의 `get_golden_set()`: golden_set.json을 직접 파싱하던 숨은 소비처였음 — 새 포맷에 맞게 턴 단위로 펼치도록 수정(안 고쳤으면 Golden Set 평가 화면이 깨졌을 것)
- `server/app/graph/state.py`: `conversation_id`/`turn_no`/`carry_schema`/`prior_turns` 필드 추가(이번 실험 시점엔 아직 어떤 노드도 소비하지 않음)

## 측정 방법

- 비교축: 없음(A/B가 아니라 baseline 최초 측정) — "후속 질문 골든셋 자체가 없던 상태" → "실측치 확보"
- 사용한 도구: `eval/execution_accuracy.py`(대화/턴 지원 버전)
- 데이터셋: `golden_set.json` 23개 대화, 28턴(싱글턴 대화 19개 + 후속 질문 포함 대화 4개)
- 재현 명령어:
  ```
  python eval/execution_accuracy.py --domain poc_prostate
  ```

## 결과

| 지표 | 값 |
|---|---|
| Execution Accuracy (전체 28턴) | 9/28 (32.1%) |
| Execution Accuracy — 턴1 (23개, 대화의 첫 질문) | 9/23 (39.1%) |
| Execution Accuracy — 턴2 (4개, 첫 후속 질문) | 0/4 (0.0%) |
| Execution Accuracy — 턴3 (1개, 두 번째 후속 질문) | 0/1 (0.0%) |
| Schema Mapping Precision / Recall / F1 | 51.2% / 66.1% / 53.8% |
| Condition Summary Faithfulness | 18/24 (75.0%) |

## 분석 및 결정

- **턴2/턴3이 정확히 0%**: 컨텍스트 주입이 아예 없는 상태에서 "그중", "거기에" 같은 후속 질문을 시키면 우연히 맞을 가능성조차 거의 없다는 뜻 — 다음 실험(intent/sql_generation에 `prior_turns` 프롬프트 주입)의 효과를 매우 선명하게 대조할 수 있는 baseline이다.
- 턴1(39.1%)이 기존 싱글턴 골든셋의 과거 측정치(EXP-001 47.4%, EXP-007 36.8%)와 비슷한 범위에서 등락하는 건 이 프로젝트의 정상적인 LLM 비결정성 범위로 보이며, 이번 변경(골든셋 확장·eval 러너 리팩터)이 기존 싱글턴 정확도에 구조적 영향을 준 것은 아니라고 판단한다 — 어떤 노드도 아직 `prior_turns`/`carry_schema`를 읽지 않으므로 논리적으로도 영향을 줄 수 없다.
- 이 실험은 "되돌릴 변경"이 아니라 골든셋·eval 러너 인프라 자체를 만든 것이고 그대로 유지하기로 했으므로 채택으로 기록한다. 이 표의 수치는 다음 실험(컨텍스트 주입)의 "변경 전" 칸으로 그대로 재사용한다.

## 새롭게 배운 것

- **모델이 후속 질문에서 "부분적으로라도" 맥락을 유추하지 않는다**: 0%라는 수치가 예상 밖이었다 — "일부는 맞히지 않을까" 생각했는데, 실제로는 매 턴을 완전히 독립된 질문처럼 처리해서 이전 필터·조인·코호트 정의를 조금도 이어받지 못했다. 즉 지금 구조에선 컨텍스트가 "약하게라도 전달"되는 우회 경로(예: 세션 내 few-shot 유사도 등)가 전혀 없다는 것을 실측으로 확인했다 — 프롬프트 명시 주입이 선택이 아니라 필수라는 근거가 됐다.
- **턴1 실패 원인 중 일부는 멀티턴과 무관한 기존 문제였다**: 신규 대화 하나("로봇 수술" 관련)의 첫 턴이 실패했는데, 원인을 까보니 술식명(`inhosp_op_eng_nm`) enum 매핑을 모델이 잘못 골라서였다(로봇 아닌 술식을 포함해 68명 대신 70명으로 오답) — 멀티턴 기능과 무관한 기존 SQL 생성 품질 이슈였다. 골든셋에 새 문항을 추가할 때 "후속 질문 실패 원인"과 "애초에 첫 턴부터 있던 기존 약점"을 섞어서 해석하면 안 된다는 걸 확인했다.

## 한계

- 후속 질문 표본이 4개 대화(턴2 4개, 턴3 1개)로 매우 작다 — 0%라는 수치의 신뢰구간은 넓게 봐야 한다. 다음 실험에서 표본을 더 늘릴지는 컨텍스트 주입 효과가 확인된 뒤 판단한다.
- 100명 합성 데이터 기준이라 EXP-001과 동일하게 절대 수치보다 "턴1 대비 턴2/3의 상대적 하락폭"에 의미를 둬야 한다.
- 단발 실행(반복 샘플링 없음) — LLM 비결정성으로 인한 분산은 이 수치에 반영돼 있지 않다.
