# [EXP-011] 스키마 후보 풀 확장(top-N 확대 + FK 1-hop + 컬럼 임베딩 히트)

- **날짜**: 2026-09-08
- **상태**: ❌ 폐기

## 배경 / 가설

외부 피드백 "RAG 임베딩 전략 구성 보완"에 대한 대응. 당시 `schema_linking`은 테이블 단위
dense 벡터 top-5만 검색해 후보를 만들고, 그 뒤 `schema_review`의 LLM 재선정(EXP-006/007,
이미 채택되어 검증됨)이 최종 테이블을 고르는 구조였다. 세 가지 개선 가설을 세웠다:

- **A. 초기 검색 폭 확대**: top-5는 좁을 수 있다. 컷오프 판단을 알고리즘(EXP-003, 실패)이
  아니라 이미 신뢰된 LLM 재선정에 맡기면, 후보를 top-8로 넓혀도 재선정기가 잡음을 걸러줄
  것이라 기대.
- **B. FK 1-hop 확장**: 질문에 직접 언급되지 않는 조인 브릿지 테이블(예: 환자 식별자만 가진
  중간 테이블)이 dense 검색에서 통째로 빠질 수 있다 — FK 그래프로 1-hop 이내 테이블을
  추가 편입하면 보완될 것이라 기대.
- **C. 컬럼 단위 임베딩**: 큰 테이블은 컬럼이 많아 테이블 전체를 뭉친 벡터에 특정 컬럼의
  의미가 희석될 수 있다 — 컬럼 단위 벡터를 별도 채널로 검색하면 테이블명/코멘트로는 안
  걸리지만 특정 컬럼이 질문과 강하게 맞는 테이블을 찾아낼 것이라 기대.

## 변경 내용

- `server/app/graph/nodes/schema_linking.py`: `_TOP_N_TABLES` 5→8(A). `_related_via_fk()` +
  `schema_provider.get_foreign_key_edges()`로 FK 1-hop 확장, 최대 3개(B). 컬럼 컬렉션 검색
  결과에서 최대 3개 추가(C). 확장된 테이블은 `_carry_over_candidates()`(기존 멀티턴
  이어받기 조립기 재사용)로 티어링해 `candidate_details`/`candidates`에 합집합으로 편입 —
  최종 채택 여부는 `schema_review`의 LLM 재선정에 그대로 맡김.
- `server/app/sql/schema_provider.py`: `get_foreign_key_edges()` 신규(도메인 전체 FK 관계를
  한 번의 쿼리로 조회, B가 사용).
- `server/app/knowledge/schema_indexer.py`: 테이블 컬렉션(`schema_{domain}`)과 별개로 컬럼당
  벡터 1개씩 `schema_columns_{domain}` 컬렉션도 색인(C가 사용).
- `server/app/domain/loader.py`: `DomainConfig.qdrant_schema_columns_collection` 필드 추가.

A/B/C를 EXP-006/007 선례대로 하나의 실험으로 묶어 측정했다.

## 측정 방법

- 비교축: 변경 전(before) vs 후(after) — 코드 자체 변경이라 런타임 토글 불가
- 사용한 도구: `eval/execution_accuracy.py --domain poc_prostate`(23대화/28턴)
- 재현: `python eval/execution_accuracy.py --domain poc_prostate`를 변경 전/후 각 1회

## 분석 및 결정

세 지표가 전부 같은 방향(악화)으로 움직여 우연이 아니라 실질적 역효과로 판단했다.
이전엔 맞던 단순 질의(예: "로봇 수술을 받은 환자는 총 몇 명인가요?"와 그 후속 질문들)가
변경 후 오답으로 바뀐 사례가 다수 관찰됐다 — 후보 테이블 수가 늘면서(5→8 + 최대 6개 추가)
`schema_review`의 LLM 재선정 프롬프트가 길어지고, 불필요한 후보가 오히려 선택을 흐린
것으로 추정된다. 이는 EXP-003~005에서 이미 반복 관찰된 "후보 풀을 넓히면 재선정기가
흔들린다"는 패턴과 일치한다 — EXP-006/007이 성공했던 건 "후보 수를 늘려서"가 아니라
"같은 후보를 더 잘 설명해서"였다는 차이를 이번에 재확인한 셈이다.

B(FK 확장)는 `get_foreign_key_edges()`로 poc_prostate 전체를 조회한 결과 **FK 제약이 단
하나도 선언돼 있지 않아**(합성 데이터셋 특성) 이번 실험에서는 실질적으로 A+C만 작동했다.
B 단독의 진짜 효과는 이 도메인으로는 검증 자체가 불가능했다.

C(컬럼 임베딩)는 실제로 새 테이블을 찾아내는 것 자체는 라이브 실행으로 확인했다(예:
`poc.poc_prostate_path`, `poc.poc_sslrdexrt`가 컬럼 히트로 후보에 추가됨) — 다만 "새 후보를
찾아내는 것"과 "정답률이 오르는 것"은 별개임을 재확인했다.

채택 기준(`kpi-experiment-log.md` 1.5절 — Execution Accuracy가 유지되거나 개선됐을 때만
채택)을 명확히 위반해 A/B/C 전량 폐기하고 코드를 원상복구했다. 신규 색인 컬렉션
(`schema_columns_poc_prostate`)도 함께 삭제했다.

## 새롭게 배운 것

- schema_review의 LLM 재선정이 "이미 검증된 안전망"이니 후보를 더 넓혀도 괜찮을 거라
  가정했는데, 실제로는 후보가 늘수록 재선정 품질 자체가 떨어지는 것으로 보인다 —
  재선정기의 신뢰도는 "후보 수"가 아니라 "후보 하나하나의 설명 품질"에서 나온다는 게
  이번에도 확인됐다.
- 이 도메인은 FK 제약이 아예 없어 FK 그래프 기반 접근(B)은 이 데이터셋으로는 검증이
  구조적으로 불가능하다 — 향후 FK가 실제로 선언된 도메인이 생기면 재시도해볼 가치가 있다.
- `_carry_over_candidates()`를 멀티턴 이어받기와 구조적 확장 양쪽에서 공유하도록
  일반화했다가 이번에 다시 원복했는데, 이런 "두 용도를 위한 조기 일반화"는 한쪽이
  폐기되면 그대로 되돌려야 해서 실익이 크지 않았다 — 다음엔 각자 별도로 둘지 먼저
  판단하는 게 나을 것 같다.

## 한계

개발 중 `schema_linking.py`를 다른 세션이 동시에 수정하고 있었다(멀티턴 `carry_schema`
기능 작업). "before" 상태를 만들기 위해 `git stash`로 이 실험의 변경분만 되돌리려 했으나,
git stash는 파일 단위로만 되돌릴 수 있어 그 세션의 미커밋 멀티턴 로직(`carry_schema`/
`prior_turns` 처리)까지 함께 사라졌다 — 즉 "before" 실행 시점엔 멀티턴 스키마 이어받기
로직 자체가 없는 상태였고, "after" 실행은 그 로직이 복원된 상태에서 A/B/C가 얹힌
상태였다. 순수하게 "A/B/C 유무"만 통제한 비교가 아니라 "멀티턴 스키마 로직 + A/B/C 유무"가
함께 바뀐 비교다.

다만 [EXP-010](./exp-010-join-validity-gate.md)의 join 검증 게이트는 양쪽 실행 모두 단 한
번도 발동하지 않아 이번 결과와 무관함을 확인했고, 표본이 작아(28턴) 개별 사례(턴 20-22)의
변화가 전체 수치에 크게 반영된다는 점도 감안해야 한다. A/B/C를 한 번에 묶어 측정해 어느
변경이 역효과의 주범인지는 특정하지 못했다(B는 무효였음이 확인됐으니 A 또는 C, 혹은 둘의
상호작용으로 추정) — 재시도한다면 반드시 하나씩 격리해서 재야 한다.
