# EXP-016 SqlValidator의 CTE 별칭 오탐 수정

- **날짜**: 2026-09-14
- **상태**: ✅ 채택

## 배경 / 가설

골든셋을 33대화/38턴(hard 6턴 포함, 기존 23대화/28턴에서 hard 표본 보강)으로 확장한 뒤
난이도별 정확도를 재보니 hard 케이스가 0/6으로 전멸했다. 6건을 각각 진단한 결과 2건
(conv12, conv15)은 `schema_review`까지는 정답 테이블을 정확히 확정했고(`schema_ok`) SQL
생성도 논리적으로 문제없어 보이는데, `validation` 단계에서 매번
"허용되지 않는 테이블입니다: path_latest" / "... robotic_op_index | ... bcr_patients | ..."
같은 에러로 거부당하고 있었다. `path_latest`, `robotic_op_index`, `bcr_patients` 모두
LLM이 생성한 SQL의 `WITH x AS (...)` **CTE 별칭**이지 실제 테이블이 아니다.

원인을 [app/sql/validator.py](../../server/app/sql/validator.py)에서 확인: `SqlValidator.validate()`가
`parsed.find_all(exp.Table)`로 SQL이 참조하는 테이블을 전부 뽑아 허용 목록과 비교하는데,
sqlglot은 `WITH x AS (...) SELECT ... FROM x`의 `x`도 `exp.Table`로 잡아낸다. CTE 이름을
제외하는 로직이 없어 CTE를 쓴 SQL은 무조건 "허용 안 된 테이블"로 오탐된다.

이건 사실 [EXP-014](./exp-014-schema-retrieval-vs-review-bottleneck.md)에서 이미 한 번 발견했던
버그다 — 그때는 `eval/execution_accuracy.py`·`eval/schema_recall_diagnostic.py`의
`_extract_tables()`(골든셋 채점용 테이블 추출 함수)에 있던 걸 고쳤는데, 정작 실서비스가 쓰는
런타임 `app/sql/validator.py`에는 같은 수정이 반영되지 않았다. `intent.py`의 hard 정의 자체가
"3개 이상 테이블 조인, 서브쿼리, 코호트 정의"라 hard 문제일수록 CTE를 쓸 수밖에 없는데,
이 버그가 hard 난이도를 구조적으로 막고 있었던 셈이다.

가설: CTE 별칭을 허용 테이블 목록 검사에서 제외하면, 논리적으로 정당한 CTE 기반 SQL이
더 이상 검증 단계에서 부당하게 거부되지 않는다.

## 변경 내용

- `server/app/sql/validator.py`: `validate()`에서 `parsed.find_all(exp.CTE)`로 CTE 별칭
  집합을 뽑아, 테이블 허용 목록 검사 시 이 집합에 속하면 건너뛰도록 수정. `eval/schema_recall_diagnostic.py`의
  `_extract_tables()`에 있던 것과 동일한 패턴을 런타임 validator에 그대로 이식.

## 측정 방법

두 축으로 나눠 측정했다 — 이 버그가 골든셋 38턴 중 정확히 2턴에만 영향을 주는 저빈도
버그라, golden set 전체 실행 1회 비교(aggregate)만으로는 신호가 노이즈에 묻힐 것으로
예상해 단위 테스트 수준 검증을 병행했다.

1. **단위 테스트 수준(결정론적)**: conv12/conv15에서 실제로 거부당했던 CTE SQL을 그대로
   `SqlValidator.validate()`에 직접 넣어 수정 전/후 결과 비교. LLM 재호출 없이 코드 변경의
   순효과만 격리해서 본다.
2. **골든셋 전체(aggregate)**: `eval/execution_accuracy.py --domain poc_prostate` 수정 전/후
   각 1회 실행 (poc_prostate, 33대화/38턴)

## 결과

### 1) 단위 테스트 수준 — 결정론적, 노이즈 없음

| SQL | 수정 전 | 수정 후 |
|---|---|---|
| conv12에서 거부됐던 CTE 쿼리(`path_latest`) | ❌ `허용되지 않는 테이블입니다: path_latest` | ✅ 통과 |
| 다중 CTE 쿼리(`a`, `b` 두 개 체이닝) | ❌ 두 CTE 모두 오탐 | ✅ 통과 |
| 실제로 없는 테이블 참조(회귀 확인용) | ❌ 정상 거부 | ❌ 정상 거부 (그대로 유지) |

### 2) 골든셋 전체(aggregate) — 노이즈 큼, 참고용

| 지표 | 수정 전 | 수정 후 | 차이 |
|---|---|---|---|
| Execution Accuracy (전체) | 15/38 (39.5%) | 13/38 (34.2%) | -5.3pp |
| Schema Mapping F1 | 78.6% | 77.9% | -0.7pp |
| Condition Summary Faithfulness | 24/26 (92.3%) | 22/31 (71.0%) | -21.3pp |

## 분석 및 결정

**단위 테스트 수준에서는 버그가 100% 재현되고 수정으로 완전히 해결됨을 확인했다** — CTE
오탐은 사라졌고 진짜 허용 안 된 테이블은 여전히 정상적으로 걸러진다(회귀 없음). 이 결과만
보면 명확한 순개선이다.

반면 골든셋 전체 실행에서는 오히려 수치가 하락했는데, 이걸 "버그 수정의 역효과"로 해석하면
안 된다 — **수정 전 코드를 코드 변경 없이 두 번(진단 스크립트 1회, execution_accuracy.py 1회)
독립 실행한 것만으로도 결과가 12/38 → 15/38로 갈렸다**(LLM 생성 SQL의 샘플링 변동만으로
±3턴, 약 8%p 차이). 이 버그가 영향을 주는 턴은 38턴 중 2턴(5.3%)뿐이라, 나머지 36턴에서
발생하는 LLM 샘플링 노이즈가 이 변경의 신호보다 훨씬 크다 — 1회 실행 aggregate 비교로는
이 정도로 저빈도인 변경의 순효과를 검출할 수 없다.

그럼에도 채택한다: (1) 단위 테스트로 버그와 수정 효과가 결정론적으로 입증됐고, (2) 이
변경은 "그동안 부당하게 거부되던 정당한 SQL을 통과시키는" 방향으로만 작동해 회귀 위험이
없으며(진짜 허용 안 된 테이블 검사는 그대로 유지), (3) hard 난이도 정의상 CTE 사용이
사실상 필수라 이 버그를 방치하면 hard 케이스는 구조적으로 계속 막힌다.

다만 이 수정 하나로 conv12/conv15가 바로 정답 처리되는 건 아니다 — conv12는 CTE 거부는
사라졌지만 재생성된 SQL의 컬럼 구성이 골든셋 기대 SQL과 달라 실행 결과 비교에서 여전히
불일치, conv15는 SQL 생성 이전의 `VALUE_UNCONFIRMED`(값 확인 실패) 단계에서 막혀 SQL 자체가
안 만들어지는 별도 문제가 남아있다. 이 수정은 "정당한 SQL이 부당하게 막히는 것"만 제거할
뿐, hard 케이스의 다른 실패 원인(retrieval_miss 4건, 값 확인 실패 등)은 그대로 남아있다.

## 새롭게 배운 것

- 같은 버그가 코드베이스 여러 곳에 독립적으로 새어 들어갈 수 있다 — EXP-014에서 이미
  `eval/`의 `_extract_tables()`에 발견해 고친 CTE 오탐 로직이, 정작 실서비스가 쓰는
  `app/sql/validator.py`에는 반영되지 않은 채 남아있었다. 이후 유사한 SQL 파싱/테이블 추출
  로직을 여러 파일에서 발견하면, 그중 하나를 고칠 때 "혹시 같은 로직이 다른 곳에도
  있나"를 먼저 확인해야 한다.
- **영향 범위가 작은(전체의 5% 수준) 버그 수정은 골든셋 1회 실행의 aggregate 지표로는
  검증할 수 없다** — 코드 변경 없이 두 번 실행한 것만으로 12/38~15/38까지 결과가 흔들렸다.
  이런 경우 aggregate 비교 대신, 실제로 버그가 발동했던 구체적 SQL을 뽑아 단위 테스트
  수준에서 수정 전/후를 직접 비교하는 게 훨씬 신뢰도 높은 증거가 된다. 앞으로 저빈도
  버그 수정은 이 방식을 기본으로 삼는다.

## 한계

- 골든셋 aggregate Execution Accuracy로는 이 변경의 순효과를 분리하지 못했다(노이즈가
  신호보다 큼) — 여러 번 반복 실행해 분산을 재는 방법이 더 정확하겠지만 이번엔 비용상
  생략하고 단위 테스트 수준 검증으로 대체했다.
- hard 케이스 6건 중 이 수정으로 직접 해결되는 것은 없다(conv12/15 모두 다른 잔여 원인으로
  여전히 실패) — 이 수정은 "검증 단계의 부당한 거부 제거"라는 필요조건일 뿐, hard 케이스
  전반의 충분조건은 아니다. 나머지 원인(retrieval_miss 4건, 값 확인 실패)은 후속 실험
  대상.
