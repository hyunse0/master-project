# [EXP-010] 조인 정합성 정적 검증 게이트 추가

- **날짜**: 2026-09-08
- **상태**: 📝 정성적 관찰

## 배경 / 가설

외부 피드백 중 "기술적 깊이가 아쉽다(join 시 성능 보장이 중요)"에 대한 1단계 대응. 당시
`validation.py`는 스키마 인용(citation) → 값 존재(anchor) → 안전성(SqlValidator) 3단만
검증하고, 생성된 SQL의 JOIN 구조가 맞는지는 아무도 보지 않았다. 조건 없는 콤마 조인이나
ON/USING 없는 JOIN은 카티션 곱(행 수 폭발)으로 이어져 성능과 정확도 두 문제를 동시에
일으킬 수 있다고 판단해, DB 조회 없이 SQL 텍스트만으로 잡을 수 있는 가장 저비용 게이트부터
추가했다(실행계획 비용 기반 게이트는 대상 DB의 EXPLAIN이 필요해 2단계로 분리, 별도 실험 대상).

## 변경 내용

- `server/app/sql/join_validator.py` 신규 — `sqlglot` AST만으로 SELECT 스코프(서브쿼리·CTE
  포함, 각자 자기 FROM/JOIN만 검사)마다 조인 조건 없이 나열된 테이블을 union-find로 탐지.
  명시적 `CROSS JOIN`은 의도된 것으로 보고 예외 처리, WHERE절 최상위 AND 등가조건으로 연결된
  구식 콤마 조인은 통과시킨다.
- `server/app/graph/nodes/validation.py` — citation보다 먼저 배선(DB 조회 불필요한 가장 싼
  검사). 실패 시 `retry_error_code="JOIN_INVALID"`로 기존 citation/anchor와 동일한 재시도
  경로(sql_generation 복귀) 사용.
- `server/app/sql/prompt_builder.py`의 `_RETRY_GUIDE`에 `JOIN_INVALID` 지침 추가.
- 프론트엔드 전체 배선: `stages.ts`(실패 스테이지 판정·체크리스트), `ValidateChecklist.tsx`,
  `EvalTab.tsx`(에러코드 라벨).

## 측정 방법

- 비교축: 게이트 추가 전(before) vs 후(after)
- 사용한 도구: `eval/execution_accuracy.py --domain poc_prostate`(골든셋 23대화/28턴)
- 로직 자체의 정확성은 별도로 10개 대표 SQL 패턴(정상 조인/카티션 콤마 조인/ON 없는
  JOIN/명시적 CROSS JOIN/체인 조인/서브쿼리 내부 카티션/USING절 등)에 대해 단위 테스트로
  직접 검증(전부 기대대로 통과/실패 판정됨).

## 분석 및 결정

poc_prostate 골든셋의 질의들은 우연히 카티션 조인을 유발할 만한 SQL을 만들지 않아, 이
게이트의 효과를 실측 정확도로 확인할 수는 없었다(양쪽 실행 모두 0건 발동). 다만:
1. 단위 테스트로 로직 자체의 정확성은 확인됨.
2. 실행 비용은 SQL 하나당 `sqlglot` 파싱 1회뿐이라 사실상 0에 가까움(DB 왕복 없음).
3. 실패 시 막는 것(카티션 곱으로 인한 응답 폭주/명백한 오답)의 기대 피해가 크고, 발동
   비용은 거의 없어 리스크 대비 기대값이 명확히 양수.

정량적 개선 근거는 아직 없지만 코드에 유지하기로 결정(✅ 채택에 가깝지만, "숫자로 효과를
확인했다"고 말할 수 없어 상태는 정성적 관찰로 남긴다).

## 새롭게 배운 것

현재 골든셋/few-shot 패턴에서는 LLM이 카티션 조인을 실질적으로 만들어내지 않는다 — 이
게이트의 진가는 이 데이터셋보다 조인이 복잡한 실서비스 트래픽이나 다대다 관계 테이블이
많은 질의에서 드러날 가능성이 크다. 골든셋에 조인이 까다로운 케이스(다대다 관계, 여러
브릿지 테이블 경유)를 추가하면 이 게이트의 효과를 정량적으로도 검증할 수 있을 것이다.

## 한계

골든셋(28턴) 안에 이 실패 유형이 0건이라 정량 효과를 주장할 근거가 없다. 정확성은 별도
단위 테스트로만 확인된 상태이며, 실제 프로덕션/더 큰 골든셋에서의 발동 빈도는 추후
관측이 필요하다.
