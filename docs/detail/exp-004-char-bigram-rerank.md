# EXP-004 Top-10 풀 + 원문 질문-스키마 char-bigram 어휘 overlap으로 최종 Top-5 재정렬

- **날짜**: 2026-08-31
- **상태**: ❌ 폐기

## 배경 / 가설

EXP-003으로 "후보 풀을 넓히기만 하는 것"은 F1 개선으로 이어지지 않는다는 게 확인됐다. EXP-002는 `intent`의 구조화 필드(영어 snake_case로 정규화된 `metric`/`dimensions`)를 검색 쿼리 텍스트에 섞는 방식이었는데, 실제 스키마 코멘트는 전부 한글이라(`schema_indexer.py`로 색인된 Qdrant payload의 `comment`/`text` 확인) 애초에 어휘가 겹칠 수 없는 조합이었다는 걸 이번에 다시 확인했다. 그래서 이번엔 `intent`를 거치지 않고 **원문 질문(한글)** 을 후보의 스키마 텍스트(테이블 코멘트+컬럼+FK가 이미 다 포함된 Qdrant payload의 `text` 필드, 재색인 불필요)와 직접 대조하면 실제 겹치는 어휘가 나올 것이라는 가설을 세웠다. 형태소 분석기가 없어(requirements.txt 확인) 어절 분리 대신 한글에 비교적 안정적인 글자 2-gram(char-bigram) overlap을 저비용 휴리스틱으로 채택했다.

## 변경 내용

- `server/app/graph/nodes/schema_linking.py`만 변경(`intent.py`/`state.py` 미변경 — 단일 변인 유지):
  - `_TOP_N_TABLES=5` 고정 조회를 `_POOL_SIZE=10`(Qdrant 조회 풀) + `_FINAL_K=5`(최종 후보 수, baseline과 동일하게 고정)로 분리.
  - `_char_bigrams()`로 원문 질문과 각 후보의 `payload["text"]`의 글자 2-gram을 만들고, `_lexical_score()` = `|질문 bigram ∩ 후보 bigram| / |질문 bigram|`로 계산.
  - `final_score = vector_score + 0.15 * lexical_score` 기준으로 풀을 재정렬해 상위 5개를 최종 후보로 확정.

## 측정 방법

- 비교축(A/B): 고정 Top-5 벡터 정렬(EXP-001 baseline) vs Top-10 풀 + 어휘 overlap 재정렬 후 Top-5
- 사용한 도구: `eval/execution_accuracy.py`
- 데이터셋: `domains/poc_prostate/golden_set.json` 19문항 — `schema_linking.py`가 EXP-003 검증 직후 즉시 baseline으로 되돌려진 상태에서 시작했으므로 EXP-001 baseline 수치를 "변경 전"으로 재사용
- 재현 명령어:
  ```
  python eval/execution_accuracy.py --domain poc_prostate
  ```

## 결과

| 지표 | 변경 전 (EXP-001) | 변경 후 | 차이 |
|---|---|---|---|
| Execution Accuracy (19문항) | 9/19 (47.4%) | 7/19 (36.8%) | -10.6pp |
| Schema Mapping Precision | 28.4% | 27.4% | -1.0pp |
| Schema Mapping Recall | 90.4% | 88.6% | -1.8pp |
| Schema Mapping F1 | 41.3% | 40.0% | -1.3pp |

## 분석 및 결정

네 지표가 전부 나빠졌고, 특히 Execution Accuracy가 10.6pp나 떨어져 EXP-002·EXP-003(둘 다 "효과 없음" 수준)보다 뚜렷한 역효과다. 원인을 확인하려고 golden_set 앞 6문항에 대해 재정렬 전/후 실제 후보 Top-5를 직접 비교했는데(임베딩 호출만 사용, SQL 생성 LLM 호출 없이 저비용으로 확인), 재정렬이 후보를 완전히 뒤집는 게 아니라 **순위 4~5위 근처에서만 미세하게 스왑**하는 정도였다(예: "다중암 여부에 따른 환자 수" 질문에서 `poc_ssnudexrt`가 빠지고 `poc_prostate_op`가 대신 들어감). 즉 α=0.15의 어휘 신호는 강하게 작동한 게 아니라 벡터 순위가 이미 애매하게 걸쳐놓은 5위 근처 후보를 살짝 흔드는 정도였는데, 이 미세한 흔들림이 19문항 중 최소 2건(#3, #11)을 OK→FAIL로 뒤집을 만큼 결과에 민감하게 작용했다. baseline recall이 이미 90%로 높다는 건 벡터 정렬이 이미 필요한 테이블을 웬만하면 Top-5 안에 넣어두고 있었다는 뜻이고, 그 마진에서 무작위에 가깝게 하나를 빼고 하나를 넣는 재정렬은 (도움이 될 확률과 해칠 확률이 반반이라면) 기댓값상 이득이 없거나 손해일 수 있다는 게 이번 결과로 뒷받침된다. `schema_linking.py`를 다시 `_TOP_N_TABLES=5` 고정 방식으로 되돌렸다.

## 새롭게 배운 것

- "언어를 맞춰서(한글 질문 vs 한글 스키마) 겹치는 어휘를 만들면 신호가 나올 것"이라는 가설 자체는 맞았다(실제로 겹치는 bigram이 나왔다) — 하지만 "신호가 존재한다"와 "그 신호가 순위를 개선한다"는 별개였다. 신호의 존재 여부보다 그 신호가 기존 신호(벡터 점수)와 결합했을 때 순위를 개선 방향으로 움직이는지가 중요하다는 걸 확인했다.
- 이 도메인은 이미 baseline recall이 90%로 높기 때문에, "이미 잘 뽑고 있는 Top-5의 경계(4~5위)를 흔드는" 종류의 개입은 이득보다 손해를 볼 여지가 더 크다 — 낮은 precision(28%)의 원인이 "순위가 나빠서"가 아니라 "K=5가 대부분의 질문이 필요로 하는 테이블 수(1~2개)보다 구조적으로 크기 때문"이라는 EXP-003의 진단과 같은 방향의 근거다. 순위를 손보는 접근(재정렬류) 전반이 이 도메인·이 baseline 상태에서는 기대만큼 여지가 없을 수 있다.
- 재정렬 실험은 "최종 지표"만 보지 말고 실제 후보 변화를 몇 개 샘플로 직접 들여다봐야 원인을 알 수 있다 — 이번에 그렇게 봐서 "완전히 다른 후보로 바뀐 게 아니라 경계선 스왑이었다"는 걸 알 수 있었고, 이게 없었다면 "재정렬 로직에 버그가 있나?" 같은 잘못된 방향으로 디버깅했을 수 있다.

## 한계

- 골든셋 19문항, 단일 실행(반복 없음) — 통계적 유의성 없음. Execution Accuracy 하락분(-10.6pp, 19문항 중 2문항)이 재정렬 때문인지 SQL 생성 단계의 비결정성 때문인지 완전히 분리되지는 않는다(다만 스키마 후보가 실제로 바뀐 질문들과 겹친다는 점에서 재정렬이 개입했을 가능성이 높다고 판단).
- 후보 변화 비교는 golden_set 앞 6문항만 샘플로 확인했다 — 19문항 전체의 재정렬 전/후 후보를 다 비교하진 않았다.
- `α=0.15`, `_POOL_SIZE=10` 조합 하나만 시도했다 — 더 작은 α라면 다른 결과가 나올 수 있으나 이번 실험에서 스윕하지 않았다.
