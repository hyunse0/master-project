# EXP-009 intent/sql_generation 프롬프트에 직전 턴 컨텍스트 주입

- **날짜**: 2026-09-08
- **상태**: ✅ 채택

## 배경 / 가설

[EXP-008](./exp-008-multiturn-golden-set-baseline.md)에서 확인했듯, `GraphState`에 `prior_turns`가 배관돼 있어도 어떤 노드도 읽지 않으면 후속 질문("그중", "거기에")은 완전히 새 질문처럼 처리돼 정답률 0%였다. 가설은 단순하다 — `intent_node`(질의 분류)와 `sql_generation`(SQL 생성) 프롬프트에 직전 턴의 질문/확정 테이블/SQL/요약을 명시적으로 얹어주면, 모델이 "그중"/"거기에" 같은 생략·대용 표현을 직전 턴 기준으로 해석하고 이전 SQL의 필터/조인을 이어받아 수정할 수 있을 것이다.

## 변경 내용

- `server/app/graph/nodes/intent.py`: `_INTENT_PROMPT`에 `{context_block}` 자리 추가, `_build_context_block()`이 `prior_turns[-1]`에서 이전 질문/확정 테이블/결과 요약을 뽑아 "이 표현들은 이전 턴 기준으로 해석하라"는 지침과 함께 삽입. `prior_turns`가 없으면 빈 문자열 — 기존 싱글턴 프롬프트와 바이트 단위로 동일.
- `server/app/sql/prompt_builder.py`: `SqlPromptBuilder.build()`에 `prior_turn_context: str | None` 파라미터 추가, 있으면 `[질문]` 블록 직전에 `[이전 턴]` 블록(이전 질문/SQL/요약 + "부정되지 않은 조건은 유지, 요구된 부분만 수정" 지침) 삽입.
- `server/app/graph/nodes/sql_generation/__init__.py`: `_build_prior_turn_context()`가 `state["prior_turns"]`를 위 형식으로 변환해 `prompt_builder.build()`에 전달.
- `schema_linking_node`(테이블 재검색 여부)는 이번 실험 범위 밖 — `carry_schema` 분기는 별도 실험(다음 단계)에서 다룬다. 이번엔 순수 프롬프트 텍스트 추가만 했다.

## 측정 방법

- 비교축(A/B): 컨텍스트 주입 전(EXP-008) vs 후(이번 변경)
- 사용한 도구: `eval/execution_accuracy.py`
- 데이터셋: `golden_set.json` 23개 대화, 28턴 — EXP-008과 동일 데이터셋
- 재현 명령어:
  ```
  python eval/execution_accuracy.py --domain poc_prostate
  ```

## 분석 및 결정

- **턴1이 정확히 동일한 개수로 유지됐다**는 점이 이 실험에서 가장 중요한 통제 결과다 — `prior_turns`가 비어있는 경로(대화의 첫 턴)는 프롬프트가 바이트 단위로 동일하므로 회귀가 있을 수 없고, 실측도 그걸 그대로 보여준다.
- 4개 후속 질문 대화 중 3개(수술종류→응급수술만, 연령대→병기 추가, 응급수술건수→병기분포)가 이번에 전부 성공했다 — 전부 "직전 턴 필터/차원 위에 하나만 얹는" 1홉 후속 질문이었다.
- 실패한 1개(로봇수술→2024년 이후→Gleason Grade Group, 턴2·턴3 모두 실패)는 애초에 **턴1 자체가 스키마 링킹 단계에서 다른 술식 테이블(`poc_opsmmsurg`)을 잘못 골라** 오답이었던 케이스라, 턴2/3의 실패는 컨텍스트 주입 실패가 아니라 "틀린 컨텍스트를 정확히 이어받은" 결과다(SQL 필터 자체는 턴1→턴2로 일관되게 이어졌음을 수동 확인). 이 대화의 턴3에서는 오히려 이어받은 로봇수술 필터 자체를 놓치고 시간 필터만 남기는 추가 열화도 관찰됐다(아래 "새롭게 배운 것" 참고).
- Execution Accuracy가 개선되고(대리지표가 아니라 진짜 지표) 다른 축도 나빠지지 않았으므로(1.5절 채택 기준 충족) 채택한다.

## 새롭게 배운 것

- **컨텍스트 주입은 "옳은 것"과 "틀린 것"을 구분하지 않고 그대로 이어받는다**: 턴1이 잘못된 테이블을 골랐을 때, 턴2는 그 잘못된 필터까지 충실하게 이어받아 개념적으로는 "맞게" 확장했다(시간 조건만 추가) — 즉 이 메커니즘은 "이전 턴이 맞았는지" 검증하지 않고 "이전 턴이 뭘 했는지"만 그대로 이어간다. 이건 설계상 당연한 동작이지만, 실측 전엔 "틀린 첫 턴이 후속 턴 실패의 원인이 되는 방식"을 이렇게 명확하게 확인하지 못했었다.
- **2홉 이상 이어지면 초기 필터가 소실될 수 있다**: 턴3(거기에 Gleason Grade Group별로도)에서 모델이 턴1의 "로봇수술" 필터는 빼먹고 턴2의 "2024년 이후" 필터만 유지한 채 새 테이블 조인을 추가했다 — 직전 1턴만 프롬프트에 넣는 지금 설계(`prior_turns` 윈도우=1)의 한계일 수 있다. 표본이 1건뿐이라 일반화하긴 이르지만, 대화가 3턴 이상으로 길어지면 윈도우를 늘리거나 "누적 확정 조건" 같은 별도 필드가 필요할 수 있다는 가설이 생겼다.
- **turn_succeeded 판정 기준(golden 정답 일치가 아니라 "생성이 끝까지 성공했는가")이 실제로 다르게 작동했다**: 턴23("수술 종류별 건수")은 golden 정답과 달라 FAIL로 집계됐지만, 그 SQL이 정상 실행됐기 때문에 턴24("그중 응급수술만")에는 정상적으로 컨텍스트가 전달됐고 턴24는 성공했다 — "정답이 아니어도 컨텍스트로는 쓸 수 있다"는 설계 의도가 실측으로 확인됐다.

## 한계

- 후속 질문 표본이 여전히 작다(턴2 4개, 턴3 1개) — 특히 턴3은 1건뿐이라 0%라는 수치에 통계적 의미를 두면 안 된다.
- 반복 샘플링 없이 단발 실행 비교라 LLM 비결정성에 따른 분산이 반영되지 않았다(EXP-008과 동일한 한계) — 실제로 턴1의 개별 문항 결과 자체는 EXP-008과 100% 동일하지 않을 수 있었으나(같은 질문도 LLM 응답이 매번 조금씩 다름), 이번엔 우연히 정답 개수(9/23)까지 일치했다.
- `carry_schema`(스키마 재검색 생략) 분기는 이번 실험에 포함되지 않았다 — 순수 프롬프트 텍스트 추가 효과만 측정했다.
